## Finding 1 — Variables counter grows by ~46 just by visiting Typography, then +1 by visiting Other

**Severity**: Medium
**Confidence**: Confirmed (reproduced 2× from a hard reload)
**User-visible**: Yes (bottom-right "Variables N" badge)
**Suspected area**: The counter that displays in the bottom-right of `packages/www/src/components/Side.tsx` (or wherever `useGlobalSearch` / variable-aggregation hook feeds it).

### What happens

The "Variables" counter at the bottom-right of the app shows different values depending on which tabs the user has visited in the current session. It only stabilizes after every tab has been touched. A user who only ever uses Colors will see 107; a user who visits Typography once will see 152; a user who also clicks Other will see 153. The number never goes back down.

This makes the counter unreliable as a "size of my framework" indicator, and creates the perception that visiting a tab somehow adds variables.

### Steps to reproduce

1. Hard reload the app (`Cmd+Shift+R`) and stay on Colors. **Observe**: "Variables 107" bottom-right.
2. Click Typography. **Observe**: "Variables 152" (jumped +45).
3. Click any of Spacing / Components / Layouts / Design / Fonts / Stylesheets. **Observe**: stays at 152.
4. Click Other. **Observe**: "Variables 153" (+1).
5. Click back to Colors. **Observe**: still **153**, even though Colors freshly showed 107 in step 1.

### Expected

The counter reflects a snapshot of the persisted preset. It should be the same number on every tab and should not change just because the user navigated.

### Actual

The counter is computed on demand from atoms that lazily populate as their owning tab is mounted. The number monotonically grows during the session.

### Evidence

- Screenshot: `./screenshots/finding-1-other-tab-counter.png` (Other tab showing 153, after a session walk)
- Repro script (run in DevTools console after reload, walks all tabs and prints the counter):

```js
for (const tab of ["Colors","Typography","Spacing","Components","Layouts","Design","Fonts","Stylesheets","Other","Colors"]) {
  // click that sidebar item, wait, read counter — see report file for full helper
}
```

Captured walk:

| Visit | Counter |
|---|---|
| Colors (fresh load) | 107 |
| Typography (first visit) | 152 |
| Spacing → Stylesheets | 152 |
| Other | 153 |
| Colors (revisit) | 153 |

### Notes

The "Selectors" counter looked stable at 707 throughout, only Variables drifts. The likely cause is that the typography/spacing modules generate their CSS variables (text-* / space-* / their auto utility classes) only when those tabs' components mount and run their effects. The counter should be computed from the canonical preset object — same source of truth that is saved to localStorage — not from atoms that hydrate on tab visit.

## Finding 2 — Save Changes button is `display: none` on mobile, blocking the primary flow

**Severity**: High
**Confidence**: Confirmed (reproduced 2×)
**User-visible**: Yes — primary save action is invisible and unreachable on mobile.
**Suspected area**: The `aside.side` element (declared in `packages/www/src/components/Side.tsx`) is hidden by a media query somewhere in `packages/www/src/styles/`.

### What happens

When the viewport drops to a typical phone width (≤ ~480 px), the entire right sidebar — which holds the **Save changes / Changes saved** button, the **Preview CSS** button, and the bottom counters — is set to `display: none`. There is no replacement UI elsewhere on the page (no bottom-bar, no FAB, no menu entry). A user on a phone can edit the framework but **cannot save** their work. The keyboard shortcut `Cmd+S` exists but is not discoverable or available on mobile devices.

### Steps to reproduce

1. Open the app at desktop width — `Save changes` button visible in the top-right.
2. Resize the browser window to 375 × 812 (or use DevTools mobile emulation).
3. Make any change (e.g. type into Project Title).
4. **Observe**: there is no Save Changes button anywhere on screen. Resizing back to ≥ 1024 px width restores it.

### Expected

Either (a) provide a mobile save affordance (bottom bar, FAB), or (b) show an explicit "Mobile editing is read-only" banner so users know they need a desktop. Silently hiding the primary action is the worst of both worlds.

### Actual

`aside.side` resolves to `display: none` at narrow widths; its only child container has `width: 0, height: 0`. Computed style chain captured:

```
BUTTON .btn-primary save-button       width=0, height=0
DIV    .grid.gap-s                    width=0, height=0
ASIDE  .side                          display: none  ← culprit
MAIN   .App                           width=345, height=733
```

There is no other button in the DOM whose text contains "Save".

### Evidence

- Screenshot: `./screenshots/finding-2-mobile-overview.png` (mobile layout, no save UI)
- Screenshot: `./screenshots/finding-2-mobile-no-save.png` (close-up showing missing right rail)

### Notes

The lack of a hamburger / overflow menu compounds this — the entire right rail (Preview CSS, counters, footer Documentation link) is also gone. Since this app is targeted at designers/developers, mobile may not be a primary use case, but at minimum the Save button needs a mobile fallback or an explicit "desktop only" notice.

## Finding 3 — Default preset ships with duplicate and malformed IDs, causing React key warnings on Manage project

**Severity**: Medium
**Confidence**: Confirmed (reproduced 2×; warnings appear on every fresh load that visits Manage project)
**User-visible**: Console-only — but **drag-and-drop in `SortableContext` is documented to misbehave with non-unique keys**, so this could surface as buggy reordering for affected items.
**Suspected area**: The seed preset file (likely `packages/core/src/data/presets.ts` or `presets-110.ts`) for `styleSheetData.layoutsStyles[0]` and `styleSheetData.typographyStyles[3]`.

### What happens

The default preset that ships with Core Framework contains:

- **Duplicate IDs**, e.g. ID `01GTC9FR7YB19JWW0R24JZCYT4` appears **7 times** under `/styleSheetData/typographyStyles/3/cssObjects/{5..9}/declarations/0` (the font-weight 100 / 200 / 300 / 400 / 500 declarations all share the same id).
- **A malformed ID** `01GXDTH123242GJHJT6XESNSE76324` (30 characters — ULIDs must be exactly 26). It appears twice under `/styleSheetData/layoutsStyles/0/cssObjects/0/declarations/0` and `…/declarations/2`.

When `Manage project` mounts, React logs:

```
Warning: Encountered two children with the same key, `01GXDTH123242GJHJT6XESNSE76324`.
  at SortableContext (@dnd-kit/sortable)
  at DndContext2 (@dnd-kit)
Warning: Each child in a list should have a unique "key" prop.
  Check the render method of `Container`.
  at Container (packages/core/src/components/presetManager/Container.tsx:19:13)
```

Beyond the noise, `SortableContext` with non-unique IDs is known to drop or duplicate items during drag, so this likely also affects reordering on the Manage project view for the affected groups.

### Steps to reproduce

1. Open the app fresh (or after `localStorage.clear()`).
2. Open DevTools → Console.
3. Click **Manage project** in the sidebar.
4. **Observe**: two `Warning: …` lines logged immediately on mount.

To verify the underlying data:

```js
// Run in DevTools console after the preset is loaded.
const cf = JSON.parse(localStorage.getItem("current_framework"));
const flat = JSON.stringify(cf);
const ids = flat.match(/"id":"([A-Z0-9]{20,})"/g) || [];
const counts = {};
ids.forEach(m => { const id = m.match(/"id":"([A-Z0-9]+)"/)[1]; counts[id] = (counts[id]||0)+1; });
const dups = Object.entries(counts).filter(([_,c]) => c > 1);
console.log("duplicates", dups);
console.log("malformed lengths", ids.map(m => m.match(/"id":"([A-Z0-9]+)"/)[1].length).filter(l => l !== 26));
```

### Expected

Every `id` in the seed preset is a fresh, valid 26-char ULID, unique across the preset.

### Actual

Six different IDs are duplicated (one of them × 7), and at least one ID is 30 characters (clearly hand-edited or concatenated by a faulty migration).

Full duplicate list captured from current localStorage:

| ID | Occurrences | Length |
|---|---|---|
| `01GXKD3G3AZVEKNBBWMXTVH59G` | 5 | 26 |
| `01GTC9FR7YB19JWW0R24JZCYT4` | 7 | 26 |
| `01GXDT320FC0HV9WQ2VJYA0NEM` | 3 | 26 |
| `01GTC7JNS21M04S04HPDHGKTHD` | 2 | 26 |
| `01GWM5EE319C9E7ZS6GBV3M6BK` | 2 | 26 |
| `01GXDTH123242GJHJT6XESNSE76324` | 2 | **30** ⚠ |

### Evidence

- Screenshot: `./screenshots/finding-3-manage-project.png` (the Manage project view that triggers the warning)
- Console output captured during full-app navigation walk: 3 warnings logged when **Manage project** mounted (transcribed in this finding's "What happens" section).

### Notes

- The 30-char ID looks like someone manually typed/edited or two ULIDs got concatenated during a one-off migration. Worth grepping the preset file for any string > 26 chars in an `"id"` field.
- Fixing this is one-shot: regenerate IDs in the seed file. No user data migration is needed because this is the *default* preset.
- Since `Container` is wrapped in a `SortableContext`, this could explain any subtle "drag picks the wrong item" reports the team has received.

## Out of scope / not logged

Things noticed but deliberately not logged (with reason):

- **Escape key does not close the Component editor modal.** Saw this on `.btn` editor. Real but Low/polish severity and a nice-to-have rather than a bug worth one of the three slots.
- **Min Screen Width can be set greater than Max Screen Width with no UI validation.** Setting min=5000 / max=1400 produces a clamp() with negative slope (font shrinks as viewport grows). This is a UX / validation gap, but the customer who would do this on purpose is probably exactly the type who knows what they're doing. Note for a future "input validation" pass.
- **Default theme dropdown initially shows "Light" but the surrounding app is dark.** Could be intentional ("default theme for the project you're building", not "current theme of the editor"). Confirmed in copy: "Select the default theme for **your project**". Working as designed.
- **`tertiary` color name renders ambiguously at 13px** — initially looked like "tertlary" but the underlying value is correct. Pure rendering artifact.
